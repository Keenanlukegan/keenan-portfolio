For Anthropic — Product Support

Production AI, shipped solo — and kept running.

A one-person production org: 39 systems shipped solo, debugged live, and kept running unattended — with human-in-the-loop safety gates on every send path.

This is what a founding-style Product Support hire looks like before the job title exists. I run a 440-student online school's entire automation estate solo — payroll engines, WhatsApp send pipelines, KPI scoring, and a self-auditing watchdog mesh — where every failure is a real person not getting paid, a parent getting double-messaged, or a class running untracked. The throughline is the discipline an AI support team actually needs: I treat unattended automations as adversaries that lie (WhatsApp Web's DOM, stale spreadsheet read-caches, silent 401s), I gate every autonomous send behind human approval, and I build observability so a failure becomes a one-glance debug instead of a multi-day silent outage.

Daily Automation Health Checker + Watchdog Mesh

Monitoring / Reliability
Live

A read-only daily agent that audits the entire automation estate and writes a dated health report, backstopped by deterministic launchd watchdogs that re-alert on Telegram if the report ever goes missing.

Why it matters

Production outcome: automations that once failed silently for days (Apr 11-13, Apr 20-29, May 8-18) now produce a single auditable daily artifact, with a 21-day clean streak visible at a glance. Engineering depth: this is observability done right under real failure modes — explicit anti-false-positive rules (cross-check Gmail against the Executions tab; reclassify stale counters after 14 days), wrapped in a model-free bash/launchd outer watchdog that has nothing that can 401. Layering a deterministic guarantee around a fallible LLM task is precisely the reliability thinking an AI support org needs.

How it works
  • Daily 08:10 WITA the checker-agent runs a 12-step read-only audit: scheduled tasks (4 expected), Cowork skills, Apps Script health (Gmail + Executions cross-check), date-aware monthly maintenance, Gmail signals, memory, blueprint alignment, wiki health
  • Writes checker-agent/DAILY_CHECK_YYYY-MM-DD.md, then reads it back and verifies it has >50 lines (silent-write guard)
  • 09:00 WITA com.cpid.daily-check-sync path-scoped commits + pushes the report to origin/main (the model never pushes itself)
  • 12:00 WITA com.cpid.daily-check-auditor pings Telegram if today's report is missing from both local and origin/main or is <50 lines, and re-alerts on every fire until cleared
  • Anti-false-positive discipline is baked in: cross-check Gmail failures against the script's Executions tab, and reclassify any counter flagged 14+ days with no live signal as 'blocked / not actionable'

CSR Cycler (WhatsApp <-> Telegram approval loop)

CSR
In progress

A Playwright-over-CDP loop that reads unread WhatsApp chats into a Sheet, routes each as a draft to the operator's Telegram for approve/edit/reject, then sends approved replies back through WhatsApp Web with post-send verification.

Why it matters

Production outcome: it handles templated CSR replies at scale without ever handing send authority to a bot — every reply is human-approved in Telegram before it leaves, and the cycler re-marks chats unread so it never hijacks the operator's own queue. Engineering depth: WhatsApp Web's DOM actively lies (it dropped message-in/out classes overnight, so direction is keyed off bubble geometry), sends are verified by re-reading the DOM (~8s poll), the loop is gated behind a file mutex when other jobs drive the same session, and a daily canary guards it. This is textbook human-in-the-loop AI ops on a hostile surface.

How it works
  • cycle.js health-checks Apps Script, acquires the WA-Web CDP lock (pausing if reminder/autolog holds it), and grants clipboard permissions on the WA origin
  • Inbound phase: wa-read.js scans unread chats and computes message direction by geometry (bubble center vs #main midline) not obfuscated .message-in/.message-out classes, captures last message + msg_id, and POSTs to /inbound
  • Apps Script dedups by msg_id, renders the template, and pushes a draft with approve/edit/reject buttons to Carla's Telegram; her tap flips the DRAFTS row to APPROVED
  • Outbound phase: cycler GETs /pending, opens each chat by phone-send-URL, clipboard-pastes the body (avoiding WA's auto-numbered-list doubling from line-by-line typing), and verifies the outgoing bubble appeared before acking /sent
  • Every chat opened for reading is re-marked unread via the chat menu so Carla's unread queue stays intact

Teacher KPI Performance Engine (Direct-Source Dispatcher)

Performance / Payroll
Shipped

A scoring engine that resolves each of 21 teacher KPIs from its true canonical source via a per-KPI fallback dispatcher, after the single legacy data source died and silently zeroed everyone's performance pay.

Why it matters

Production outcome: when a deprecated sheet permanently emptied, every teacher silently scored 'no data' and earned Rp 0 on performance pay — a live incident with real money on the line. Engineering depth: the fix is a resolveKpiScore_ fallback chain (true source → manual entry → graceful N/A) with a resolvedSource audit column that makes every score's provenance debuggable at a glance, and it was made purely HTTP-callable so a future cloud cutover needs no rework. Resilient fallbacks plus provenance-as-observability is exactly the post-incident pattern an AI support team prizes.

How it works
  • resolveKpiScore_(kpiId, ctx) runs a fallback chain per KPI: direct source -> Manual KPI Entry tab -> template -> overrides -> Evaluasi TC fallback -> null
  • 6 KPIs auto-score from real sources: #6 Jadwal lengkap/rapi, #8 Attendance Report H-day, #10 Tepat istirahat <13:00, #11 Absen Pagi/Closing, #13 Student Attendance, #18 Retention >=90% over 6mo (#18 returns null until July 2026 for lack of baseline); #19 Notes Masalah surfaces data as judgment context
  • Each KPI Scores row gets a resolvedSource column (direct / manual-entry / template / override / evaluasi-tc-fallback / no data) so a still-failing tier is diagnosable
  • Tier-pass rule gates pay: a teacher passes a weight tier only if ALL KPIs at that weight score >=80; missing data counts as failing

CRM Autolog (WhatsApp -> CRM auto-ingest)

CRM
Live

A launchd job that every 4 hours opens unread WhatsApp chats, classifies and logs the latest messages into a CRM sheet with a replied/unreplied flag, then re-marks each chat unread to preserve the follow-up queue.

Why it matters

Production outcome: it turns a live WhatsApp inbox into structured CRM rows automatically, so leads and complaints stop falling through the cracks. Engineering depth: this is a real post-incident story — reading a chat marks it read on the linked phone, which once caused a 'my WhatsApp read itself for days' outage. The fix shows operational rigor: the old re-mark used a synthetic hover that failed ~100% of runs silently, rewritten to a right-click menu with explicit badge verification, retry, and a state-file record of any miss. Turning an invisible failure into an auditable one is the support-engineering instinct.

How it works
  • launchd fires the script every 4h; it acquires the shared WA-Web CDP lock for the entire scrape
  • findUnreadChats scans the WA Web chat list for [aria-label*=unread i] badges
  • For each unread chat it opens by exact name, extracts recent messages, computes direction (In/Out) and a replied flag (any later outgoing message after the inbound), and collects rows
  • Collected chats are POSTed (token-authed) to the CRM web app, which logs them and rebuilds the one-row-per-student Students view
  • reMarkUnread right-clicks the chat row -> 'Mark as unread' / 'Tandai belum dibaca', then verifies the unread badge returned (with one retry); failures are logged and written to .autolog-last-run.json

Art Journey Student Report Generator

Reporting
Shipped

A standalone Apps Script that clones one parent-facing report sheet per active student from a master template and fills it with each child's real data — profile, level, artworks, scores, payment, history, certifications.

Why it matters

Production outcome: it generated 440 individualized parent reports in one batch with zero errors, turning scattered source sheets into a self-updating magazine-style document per student and cutting the constant stream of parent questions.   • Drive images are embedded as cell-image values after sharing ANYONE_WITH_LINK so the lh3.googleusercontent CDN URL resolves
  • A resumable Playwright CDP driver chunks the full batch and records done-IDs so a multi-hour run can stop and continue

Cowork-Bot — Telegram-to-Claude Agentic Bridge

Agentic OS
Live

A long-polling Telegram bot that routes each message to a fresh headless Claude Code run inside the repo, turning chat into a permission-gated agent over the whole automation estate.

Why it matters

Production outcome: a solo operator can drive the entire repo from a phone without exposing a dangerous shell. Engineering depth: each message becomes a headless `claude --print` in the repo working dir, so the agent auto-inherits every CLAUDE.md rule and the settings.json allowlist — no second agent to secure. How it works

  • Each accepted message spawns `claude --print` in the repo dir with a 10-minute timeout; errors return an error reply to the chat
  • Claude obeys the settings.json allowlist (no skip-permissions), so the bot's agency is bounded by the same gates as the CLI
  • A separate morning-brief LaunchAgent pushes a filtered daily brief — Keenan's full engineering brief vs Carla's filtered bucket

CPID Daily WhatsApp Class-Reminder Sender

Scheduling / Messaging
Live

An unattended morning job that reads the day's roster and sends each guardian a per-student WhatsApp reminder by driving WhatsApp Web through Playwright — with three dedup guards and post-send DOM verification.

Why it matters

Production outcome: a daily manual chore became an unattended launchd job covering a roster that scales by weekday (Wed 42, Sat 52). Engineering depth: this is the defensive-correctness story support engineers live in — WhatsApp Web's DOM lies (chats mis-open, keystrokes get eaten, history renders in two locales), so a naive sender double-sends to parents or logs SENT for messages that never landed. Phone-first chat opening, three concentric dedup guards, and post-send DOM verification were each paid for by a real mis-send. Treating 'I pressed Enter' as a hypothesis, not a fact, is exactly the rigor flaky third-party surfaces demand.

How it works
  • launchd fires the wrapper at 05:06 WITA Mon-Sat; a CDP preflight (check-cdp.js, 10s) does a real connectOverCDP handshake and bails fast with a Telegram alert if Debug Chrome is wedged, rather than stalling on Playwright's 120s connect timeout.
  • Stage 1 commits pre-typed drafts (--send-drafts); stage 2 runs ONLY if the stage-1 JSON reports composeInvalid > 0 (the only failures a direct re-send can fix) — both stages share a /tmp roster cache so a mid-run MASTER edit can't split the phone data.
  • Per student: open chat via web.whatsapp.com/send/?phone=62... (never name-search, which once mis-sent to a 'BUKTI PEMBAYARAN' chat), with up to 3 page.goto auto-retries and a name-search fallback for wrong/missing CONTACTS phones.
  • Three dedup guards before any send: SEND LOG sheet pre-filter, dual-anchor DOM check (today-dated bubble that contains BOTH 'pengingat otomatis' AND the student's full name), and an eyeball-the-rendered-text step for locale drift (Indonesian 'Kamis' vs 'Thursday').
  • After pressing Enter, verifyDeliveredToday() polls the DOM for a new today-stamped reminder bubble before logging SENT; on timeout it logs FAILED — added after an audit found 23 of 40 logged-SENT messages never delivered.
  • Unread-badge preservation re-marks any chat that had an unread incoming customer message, so reminder sends don't silently empty Carla's to-do queue; every outcome (SENT/VERIFIED/FAILED/SKIP) is appended to SEND LOG and the final summary is upserted into the CRM 'Reminder Daily' tab.
