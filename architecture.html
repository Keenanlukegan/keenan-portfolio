How I think

Structure is the intelligence

The agent is generic. The architecture is the IP.

The model will change every few months. The durable value isn't the agent — it's how the system is built: what's impossible by design, where truth lives, how it fails, and how its knowledge is structured. I build on two patterns and operationalize them for a real business:

Folder-structure-as-architecture — the Interpreted Context Methodology. The intelligence lives in a deliberately layered context (numbered stages → CONTEXT.md routing → reference → artifacts), read by one generic agent — not a bespoke agent per task. Swap the model; the structure holds.

A self-maintaining second brain — Karpathy's LLM-wiki pattern. The company's knowledge lives in an interlinked, self-linting knowledge base the system maintains itself, so it inherits memory instead of rebuilding it every session.

The architecture

One operator, a structured system, a whole business

How I made the calls

Architecture Decision Records

An architect is judged by their decisions. Each of these is a real call forced by a real situation — most of them by a real failure. Click any one to open it.

ADR-01Structure is the architecture; the agent is generic+
Context
The default is a bespoke agent per task — a framework graph, prompts wired to tools. That puts the intelligence in the part that changes underneath you: the model.
Decision
Follow the Interpreted Context Methodology: put the intelligence in a layered context — numbered stage folders, CLAUDE.md → CONTEXT.md routing, reference + artifact layers — and let one generic agent read the right files.
Why
Agents are interchangeable; a well-structured context is durable and model-agnostic. The folder structure is the program.
Result
agency-os runs jobs through numbered stage folders (00-draft/, 10-send/), each scoped by its own CONTEXT.md. No framework, no per-task agent.
ADR-02Give the company a second brain that maintains itself+
Context
Knowledge lived in people's heads and scattered chats. Every session re-derived the same context; every new helper started cold.
Decision
A persistent, interlinked markdown wiki the LLM builds and maintains (Karpathy's pattern). Sources immutable; pages organized by knowledge type; a weekly linter catches drift; the log is append-only.
Why
A self-maintaining knowledge layer means the system — and any new maintainer — inherits memory instead of rebuilding it.
Result
A live ~11-category second brain with a self-correcting lint that catches real drift (a stale KPI count; a blocker assigned to departed staff).
ADR-03Make "no unapproved send" structural, not behavioral+
Context
The support agent drafts replies to real parents. "Don't send without approval" as a code rule is one bug away from an AI texting a customer.
Decision
The send path can only read a server-side queue returning only human-approved, unsent rows. Approval is a state change a human triggers; no code path sets it automatically.
Why
A safety property you can prove from the data flow beats one you trust the code to honor. The unsafe state is unreachable.
Result
Even a crashing sender physically cannot send an unapproved message. Zero unreviewed sends.
ADR-04Open chats by phone, never by name+
Context
A reminder once went to the wrong chat — a name search matched a different conversation and the bot sent into it, logging success. Caught only by manual audit.
Decision
Outbound messaging opens a chat by phone number via a deterministic deep link. Name-based resolution is banned.
Why
Names are ambiguous; a phone number is a unique key. A student with no phone is skipped, not guessed — the safe failure direction.
Result
Eliminated the wrong-recipient class of error.
ADR-05The watcher must not share a failure domain with the watched+
Context
A two-day silent outage: the scheduler fired, but an auth error meant the orchestrator never woke — so nothing sent and no alert fired, because the alerting lived inside that same orchestrator.
Decision
An independent auditor — pure bash + curl, no model, no shared runtime — checks for the expected output each morning and pings Telegram if it's missing.
Why
Inline error handling can't report a failure that stops it from running. The monitor must fail independently of what it watches.
Result
Silent failures became loud — "no run" and "partial run" are caught even when the primary stack is dead.
ADR-06Use the model only where judgment is needed; cron is not judgment+
Context
Deterministic "run this script daily" jobs were running through a model-driven scheduler, adding auth/availability failure modes to work that needed no reasoning.
Decision
Pure scheduled work runs on the OS scheduler (launchd). The model-driven scheduler is reserved for jobs that genuinely need reasoning.
Why
Don't put an LLM on the critical path of work that doesn't need one — every dependency is a failure mode.
Result
Removed a fragile dependency from the reliability-critical reminder job.
ADR-07One source of truth per fact+
Context
Teacher KPIs could be hand-entered or re-derived in several places — drift and disputes, and these numbers change someone's pay.
Decision
Each KPI is scored from exactly one named authoritative system (uploads from Drive, attendance from the check-in bot, retention from the enrollment sheet). The gradebook references sources; it doesn't re-keep them.
Why
A fact with two homes will eventually disagree with itself. Traceability is what makes an automated grade defensible in a payslip.
Result
Every KPI score traces to a source; subjective ones route to a human override instead of a second source of truth.
ADR-08Place every automation on the autonomy dial deliberately+
Context
"How much should this run on its own?" differs for a customer reply vs a reminder vs an internal report — and a non-technical owner has to trust the whole fleet.
Decision
Every automation is placed on draft → auto → gated by two tests: is it reversible, and is it customer-facing? Customer-facing or irreversible ⇒ gated, always.
Why
A consistent, legible safety model across the fleet beats per-automation cleverness. The owner reasons about the whole system with one rule.
Result
A non-technical owner can predict what any agent will and won't do on its own.

Field notes — real edge cases I diagnosed running Claude Code in production. The texture of an actual support ticket, answered from having lived it. Click to open.

NOTEHeadless auth ≠ interactive auth+
Symptom
A scheduled job did nothing for two days — and sent no alert.
Cause
My interactive claude was authed the whole time, but the headless / Desktop-spawned sessions threw ~3,000 401s at every fire window. The orchestrator never woke, so it never reached its own error-reporting.
Fix
An independent canary that can't share the failure domain, and moving deterministic cron off the model-driven path entirely.
NOTEUnattended runs hang on a permission-prefix mismatch+
Symptom
A cron task fired but hung instead of running.
Cause
The prompt issued cd "…" && node script.js, which didn't match my allow-list prefix Bash(node …wa-remind-send.js *) — so it waited for a permission tap no human was there to give.
Fix
Match allowed-tool prefixes to the exact command shape for headless runs; add a watchdog for "waiting on input that'll never come."
NOTECron isn't judgment — don't put the model on its critical path+
Symptom
Reliability-critical daily jobs inheriting auth / availability failures they didn't need.
Cause
Deterministic "run this script" work was routed through a model-driven scheduler — adding the whole LLM dependency to work that needs no reasoning.
Fix
Pure cron → launchd; reserve the model-driven scheduler for jobs that genuinely reason. Knowing where not to use the model is the skill.

About

Why I build it this way

I'm a Singaporean systems architect. For the past year I've designed and run the entire operations of a small art school in Bali on a system I architect and maintain myself — customer comms, deliverable production, staff performance, scheduling, reporting, the monitoring that watches all of it, and the second brain that remembers it.

The hardest part was never the code. It was earning the trust of a non-technical owner who has to live with whatever the system does to her business and her customers. That's why everything starts gated, why nothing irreversible goes out without a sign-off, why every unattended job has a watcher, and why I treat the structure — not any one agent — as the thing worth getting right. Responsible, human-in-the-loop AI isn't a slide here; it's the only way a real person was ever going to let me run their company on it.

I'm building toward applied / forward-deployed AI work, where that same instinct — architect real agentic systems into a real business, carefully — is the whole job.
