How I think

The architecture is the part that lasts

The agent is interchangeable. The architecture around it is what I actually built.

The model changes every few months. What lasts is how the system is built: what the code makes impossible, where the source of truth lives, how it behaves when things break, and how the knowledge is organized. I built on two existing patterns and put them to work for a real business.

Folder-structure-as-architecture, the Interpreted Context Methodology. The intelligence lives in a layered context (numbered stages → CONTEXT.md routing → reference → artifacts), read by one generic agent rather than a custom agent per task. Swap the model and the structure holds.

A self-maintaining second brain, Karpathy's LLM-wiki pattern. The company's knowledge lives in an interlinked, self-linting knowledge base the system keeps current itself, so it inherits memory instead of rebuilding it every session.

The architecture

One operator, a structured system, a whole business

CPID is an established Bali art school. It has 300 monthly active students today and 5,000+ taught across its ~10 years, run by a non-technical founder. How I made the calls

Architecture Decision Records

Each record below is a real call forced by a real situation, most of them by a failure. Click any one to open it.

ADR-01Put the intelligence in the structure, not the agent+
Context
The default is a custom agent per task: a framework graph, prompts wired to tools. That puts the intelligence in the part that changes underneath you, the model.
Decision
Follow the Interpreted Context Methodology. Put the intelligence in a layered context (numbered stage folders, CLAUDE.md → CONTEXT.md routing, reference and artifact layers) and let one generic agent read the right files.
Why
Agents are interchangeable. A well-structured context is durable and model-agnostic. The behavior comes from the folder layout, not from agent code.
Result
agency-os runs jobs through numbered stage folders (00-draft/, 10-send/), each scoped by its own CONTEXT.md. No framework, no per-task agent.
ADR-02Give the company a second brain that maintains itself+
Context
Knowledge lived in people's heads and scattered chats. Every session re-derived the same context. Every new helper started cold.
Decision
A persistent, interlinked markdown wiki the LLM builds and maintains (Karpathy's pattern). Sources stay immutable, pages are organized by knowledge type, a weekly linter catches drift, and the log is append-only.
Why
A self-maintaining knowledge layer means the system, and any new maintainer, inherits memory instead of rebuilding it.
Result
A live ~11-category second brain with a self-correcting lint that catches real drift: a stale KPI count, and a blocker assigned to departed staff.
ADR-03Make "no unapproved send" a structural property of the data flow+
Context
The support agent drafts replies to real parents. "Don't send without approval" as a code rule is one bug away from an AI texting a customer.
Decision
The send path can only read a server-side queue that returns only human-approved, unsent rows. Approval is a state change a human triggers. No code path sets it automatically.
Why
A safety property you can prove from the data flow beats one you trust the code to honor. The unsafe state is unreachable.
Result
Even a crashing sender physically cannot send an unapproved message. Zero unreviewed sends.
ADR-04Open chats by phone, never by name+
Context
A reminder once went to the wrong chat. A name search matched a different conversation and the bot sent into it, logging success. Manual audit was the only thing that caught it.
Decision
Outbound messaging opens a chat by phone number via a deterministic deep link. Name-based resolution is banned.
Why
Names are ambiguous. A phone number is a unique key. A student with no phone is skipped, not guessed, which is the safe direction to fail.
Result
Eliminated the wrong-recipient class of error.
ADR-05The watcher must not share a failure domain with the watched+
Context
A two-day silent outage. The scheduler fired, but an auth error meant the orchestrator never woke. So nothing sent and no alert fired, because the alerting lived inside that same orchestrator.
Decision
An independent auditor (pure bash and curl, no model, no shared runtime) checks for the expected output each morning and pings Telegram if it's missing.
Why
Inline error handling can't report a failure that stops it from running. The monitor must fail independently of what it watches.
Result
Silent failures became loud. "No run" and "partial run" are caught even when the primary stack is dead.
ADR-06Use the model only where judgment is needed; cron is not judgment+
Context
Deterministic "run this script daily" jobs were running through a model-driven scheduler, adding auth/availability failure modes to work that needed no reasoning.
Decision
Pure scheduled work runs on the OS scheduler (launchd). The model-driven scheduler is reserved for jobs that genuinely need reasoning.
Why
Don't put an LLM on the critical path of work that doesn't need one. Every dependency is a failure mode.
Result
Removed a fragile dependency from the reliability-critical reminder job.
ADR-07One source of truth per fact+
Context
Teacher KPIs could be hand-entered or re-derived in several places. That meant drift and disputes, and these numbers change someone's pay.
Decision
Each KPI is scored from exactly one named authoritative system (uploads from Drive, attendance from the check-in bot, retention from the enrollment sheet). The gradebook references sources. It doesn't re-keep them.
Why
Two copies of the same KPI eventually drift apart. Traceability is what makes an automated grade defensible in a payslip.
Result
Every KPI score traces to a source. Subjective ones route to a human override instead of a second source of truth.
ADR-08Place every automation on the autonomy dial deliberately+
Context
"How much should this run on its own?" differs for a customer reply vs a reminder vs an internal report, and a non-technical owner has to trust the whole fleet.
Decision
Every automation is placed on draft → auto → gated by two tests: is it reversible, and is it customer-facing? Customer-facing or irreversible means gated, always.
Why
A consistent, readable safety model across the fleet beats per-automation cleverness. The owner reasons about the whole system with one rule.
Result
A non-technical owner can predict what any agent will and won't do on its own.

Field notes: real edge cases I diagnosed running Claude Code in production. These are real edge cases I hit and fixed. Click to open.

NOTEHeadless auth ≠ interactive auth+
Symptom
A scheduled job did nothing for two days, and sent no alert.
Cause
My interactive claude was authed the whole time, but the headless and Desktop-spawned sessions threw ~3,000 401s at every fire window. The orchestrator never woke, so it never reached its own error-reporting.
Fix
An independent canary that can't share the failure domain, and moving deterministic cron off the model-driven path entirely.
NOTEUnattended runs hang on a permission-prefix mismatch+
Symptom
A cron task fired but hung instead of running.
Cause
The prompt issued cd "…" && node script.js, which didn't match my allow-list prefix Bash(node …wa-remind-send.js *), so it waited for a permission tap no human was there to give.
Fix
Match allowed-tool prefixes to the exact command shape for headless runs, and add a watchdog for "waiting on input that'll never come."
NOTECron isn't judgment: don't put the model on its critical path+
Symptom
Reliability-critical daily jobs inheriting auth and availability failures they didn't need.
Cause
Deterministic "run this script" work was routed through a model-driven scheduler, which added the whole LLM dependency to work that needs no reasoning.
Fix
Pure cron moved to launchd, and the model-driven scheduler is reserved for jobs that genuinely reason. A lot of the work is deciding where the model shouldn't run at all.

About

Why I build it this way

I'm a Singaporean systems architect. For the past year I've built and run the entire operations of a small art school in Bali on a system I maintain myself: customer comms, deliverable production, staff performance, scheduling, reporting, the monitoring that watches all of it, and the second brain that remembers it.

The hardest part was never the code. It was earning the trust of a non-technical owner who has to live with whatever the system does to her business and her customers. That's why everything starts gated, why nothing irreversible goes out without a sign-off, why every unattended job has a watcher, and why I treat the structure, not any one agent, as the thing worth getting right. None of this was theoretical. A non-technical owner only let me run her company on AI because nothing irreversible could go out without her sign-off.

The day-to-day of that work is the support job: someone hits a wall with the product, I figure out why and get them moving again. When the system goes dark I'm the one who finds it. The two-day outage was me debugging a silent 401 stack until I had the cause, then building a daily health-checker so a silent failure can't hide that long again. That is on-call incident response, and I've been doing it for a year. I've done the customer-facing half too. At Sleek, a banking-as-a-service fintech, I grew a client base from 25 to 300, moved monthly active users from 10% to 30%, migrated over 1,000 clients onto a new platform, and resolved every product issue my clients hit, working across our own teams and external ones including DBS, to a positive NPS. I haven't held a support-queue title or carried a pager before. A founding APAC hire builds the support function rather than inheriting a queue, and I've already done both halves. I want to do this for Anthropic's users.
